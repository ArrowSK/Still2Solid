# Milestone M4 — Learned local timing and ETA

## Goal

Replace static or first-run-only progress guesses with timing estimates learned from successful generations on the user's own hardware, while keeping the data local and keeping progress explicitly estimated rather than pretending it is exact.

## Delivered

- Local timing profile keyed by:
  - hardware fingerprint;
  - model ID and model version;
  - quality preset;
  - requested backend (`auto`, Metal/MPS, CUDA or CPU);
  - foreground-isolation setting.
- Per-stage duration extraction from the existing M3 worker progress stream.
- Median-based total and per-stage statistics.
- Learned ETA and weighted overall percentage on comparable later runs.
- ETA confidence levels that increase only after enough consistent samples exist.
- Smooth local countdown between worker progress events without inventing new worker steps.
- Advanced-mode diagnostics showing:
  - learned-run count;
  - confidence;
  - median total duration;
  - variability;
  - per-stage median durations;
  - recent successful completions and resolved backend.
- One-click reset of only the currently selected timing profile.
- Version bump to `0.4.0`.

## Privacy and persistence

Timing data is stored only in the desktop webview's local storage under schema-versioned key `still2solid.timingProfiles.v1`.

The timing store contains configuration fingerprints and durations only. It does not store source images, filenames, generated assets, prompts, account data or network identifiers. No timing information is uploaded and there is no telemetry endpoint.

Profiles are bounded to 24 recent observations each and 40 profile combinations globally to avoid unbounded local-storage growth.

## Learning rules

Only a generation that returns a successful TripoSR result is eligible for learning.

- Cancelled generation: ignored.
- Failed generation: ignored.
- Successful generation: recorded.
- Implausible duration below 0.25 s or above 2 h: excluded from learned statistics.
- Once four accepted samples exist, a new successful sample below one-third or above three times the current median is retained in recent diagnostics as `excluded`, but it does not influence future ETA statistics.

This keeps transient thermal throttling, system sleep, debugger pauses and unusual contention from permanently distorting the ETA model while still making the event visible to an advanced user.

## ETA calculation

The first comparable run has no learned ETA. Still2Solid continues to show the real M3 worker stage and its existing stage percentage, with text explaining that timing is being learned.

After at least one accepted comparable run:

1. The median duration of each observed stage becomes that stage's expected weight.
2. Overall progress is calculated from completed expected stage time plus the current stage fraction.
3. Remaining time is the expected unfinished fraction of the current stage plus all expected later stages.
4. Between worker events, Still2Solid advances only the **estimated** current-stage fraction using the learned median duration and caps that interpolation before stage completion. The next real worker event remains authoritative.

The UI always describes this as learned/estimated timing. It does not present the profile as deterministic completion time.

## Confidence

Confidence is intentionally conservative:

- fewer than 2 accepted samples: `low`;
- 2–5 accepted samples: at most `medium`, depending on variability;
- 6+ accepted samples: `high` only when median absolute deviation is low enough;
- highly variable histories remain `low` or `medium` regardless of sample count.

## Compatibility behaviour

A timing profile never changes model compatibility, memory policy, runtime verification or model selection. M4 only estimates time/progress for a generation path already approved by M2/M3.

Changing any of the following selects a separate timing profile rather than mixing incompatible observations:

- hardware;
- model/model version;
- Fast / Standard / Best;
- backend choice;
- foreground isolation on/off.

This also means changing the model version automatically starts a clean timing history without deleting older local records.

## Acceptance criteria

- [x] M1–M3 generation, cancellation, fallback, installation and preview behaviour remain unchanged.
- [x] First production run does not display a fabricated learned ETA.
- [x] Successful production runs persist timing data locally.
- [x] Failed and cancelled runs do not affect profiles.
- [x] Extreme outliers do not affect medians after a baseline exists.
- [x] Comparable subsequent runs use learned stage weights for ETA and overall progress.
- [x] ETA visibly carries a confidence level.
- [x] Advanced mode exposes local timing diagnostics/history and profile reset.
- [x] Simple mode remains uncluttered.
- [x] Timing storage is bounded and contains no image/asset content.
- [x] Unit tests cover medians, sparse-stage extraction, outlier handling and learned ETA calculation.
