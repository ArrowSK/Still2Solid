# Milestone M5 — Canonical asset and export pipeline

## Goal

Turn the direct M3 GLB download into a model-agnostic production asset layer with explicit format semantics, without changing inference, learned ETA or print-repair behaviour.

## Delivered

- Treats each production generation as a canonical GLB 2.0 master.
- Validates the GLB header and exact declared byte length before export.
- Locally inspects:
  - file size;
  - mesh count;
  - vertex count;
  - triangle count;
  - material count;
  - texture count;
  - geometric bounds.
- Replaces the single production `Export GLB` action with a compact export workspace.
- GLB export downloads the exact master bytes without re-encoding.
- OBJ compatibility export creates one ZIP containing:
  - `.obj` geometry/UVs/normals;
  - `.mtl` material library;
  - PNG base-colour and normal maps when browser-readable;
  - `asset.json` conversion manifest.
- STL export creates binary geometry-only STL.
- All conversions are performed locally in memory.
- The canonical GLB is never replaced or mutated by a derived export.
- Adds deterministic filename sanitization and export validation helpers.
- Adds unit tests for GLB validation, filename handling and file-size formatting.
- Adds `fflate` (MIT) for client-side ZIP creation.
- Version bumped to `0.5.0`.

## Format semantics

### GLB — fidelity-preserving master

This is the default/recommended export. Still2Solid downloads the exact bytes generated by the production worker after local GLB validation.

No conversion is performed, so embedded textures/materials are preserved as generated.

### OBJ + MTL + textures — compatibility export

OBJ/MTL is widely compatible but materially less expressive than GLB/glTF PBR.

M5 therefore does not claim an OBJ package is visually equivalent to the canonical master. It maps what the legacy format can represent:

- geometry;
- normals;
- UV coordinates;
- material names;
- diffuse/base colour;
- opacity;
- base-colour texture where readable;
- normal texture where readable.

The ZIP manifest explicitly records that this is a compatibility conversion and that the GLB remains the master.

### STL — geometry-only downstream export

Binary STL is provided for compatibility with mesh and slicing workflows.

Still2Solid explicitly warns that STL:

- stores no textures;
- stores no colours in a portable way;
- has no reliable unit metadata;
- is not evidence that the mesh is manifold or watertight.

Therefore M5 does **not** label STL as print-ready.

## Why 3MF is not in M5

3MF is intentionally deferred to M6 together with explicit sizing, units, orientation, manifold/watertight analysis and automatic repair. Emitting a 3MF file before those semantics exist would imply a stronger printing contract than Still2Solid can currently guarantee.

## Privacy and security

- No export leaves the machine except through the user's explicit file download/save action.
- No generated geometry, material or texture is uploaded.
- Export conversion opens no network service.
- Model runtimes and their permissions are unchanged.
- M4 timing profiles are unchanged.

## Acceptance criteria

- [x] Existing M1–M4 generation, Model Manager, timing and cancellation behaviour is preserved.
- [x] Production GLB is validated before derived export.
- [x] Exact GLB master can be downloaded unchanged.
- [x] OBJ export is packaged with MTL and available textures rather than emitting a misleading bare `.obj`.
- [x] OBJ UI states that PBR fidelity is reduced.
- [x] STL UI states that colour/texture/units are not preserved.
- [x] Derived export never changes the canonical master.
- [x] Export pipeline is local-only.
- [x] Unit tests cover core validation/naming helpers.
- [x] CI must pass Svelte/TypeScript checks, unit tests, frontend build, worker syntax, Rust compilation and Rust tests before merge.

## Deferred

- M6: print analysis, repair, explicit units/sizing/orientation, flat-base tooling and 3MF.
- M7: signed/notarized release packaging with bundled end-user runtime.
